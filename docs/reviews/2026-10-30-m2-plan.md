## 3. 结论

**`CHANGES-REQUESTED`**

M2 的方向（单进程 axum/PG、弱管控、仅 Responses、角色/钱包/审计、企业客户端裁剪）与 `docs/06/07/12` 的 M2 目标一致；docs/28 的“按交互面拆/按耦合合并”也基本符合三份 research 事实。但当前 M2 spec **不能改 approved**，原因是：

1. **P0 安全/SSOT 冲突**：管理台认证边界与 `docs/06/04/21` 的 Cookie session + CSRF 规范冲突，且 spec 完全没有管理台登录/CSRF 约定；
2. **M2 切点覆盖不足**：auth 三入口、JWT refresh/epoch、钱包 hold/并发/峰谷、网关 `/v1/models`/未定价错误、bootstrap 路径、审计哈希链/WORM、docker/备份、企业客户端裁剪均有缺失或与规范冲突；
3. **C3/C4 不可执行**：design 的包名/契约名未按 `docs/02 §5`、`docs/07 §9`、`docs/24 §1.5` 登记；管理台页面包缺失；迁移/路由/权限生成物没有可执行门禁；
4. **docs/28 仍有硬冲突/事实错误**：与 `docs/19` 的 `ui.composer`/工具状态词汇、与 `docs/27` 的 288 旧值描述不一致；骨架 props 与已落地 skeleton 组件不一致。

修完 P0/P1、补 P2 后，才能判定 M2 spec 是否 approved。

## 4. P0（阻塞）

### P0-1 · 管理台认证/CSRF 与 docs/06/04/21 冲突，spec 未定义管理台入口

**证据**

- `design.md:14`：`/admin/*` 使用 **管理员 JWT + 权限点**；
- `docs/06:71-81`：管理台是 `/api/admin/*` + `/admin/*`，**Cookie session + CSRF**；员工 JWT 与管理 cookie 物理分离；
- `docs/04:143`：管理端独立 Cookie 会话（HttpOnly/SameSite/CSRF；12h/60min idle）；明确“客户端 JWT 不得用于管理面”；
- `docs/21:35`：管理台独立 Cookie+CSRF；`docs/21:37` 要求失败锁定/限速/来源限制；
- M2 `spec.md:33-39` 只有 `/api/auth/login|refresh|logout`，没有 `/api/admin/auth/*`、CSRF、管理台登录、审计员只读权限；`design.md:13` 只写 `auth(JWT/cookie)`，未定义哪个入口用哪种凭据。
- 结果：approved 后实现者会得到两个互斥的认证方案，且有可能把员工 JWT 用于管理面——这是管理台权限提升/CSRF 风险。

**修法**：按 `06/04/21` 冻结管理台为 Cookie session + CSRF；在 M2 spec 增加管理台登录/登出/CSRF token/失败锁定/来源限制/审计员只读路由与权限矩阵；删除 design 的“`/admin/*` 管理员 JWT”表述；补 e2e：员工 JWT 调用 `/api/admin/*` 必须 401/403、无 CSRF 写操作必须拒绝。

### P1-2 · 客户端认证/API 覆盖不完整；JWT 安全细节不足

- **管理台入口**见 P0-1；spec 还缺 `/api/session`/admin 登录；
- **JWT**：`spec.md:35-39` 只有 15m/30d/epoch；`docs/04:136-140` 要求 EdDSA、`kid` 轮换、refresh 不透明串/hash/reuse 检测、`device_id`+`channel` 绑定、旧 refresh 重放吊销设备族；`docs/21:34` 同。spec 的 `refresh_tokens` 表（`:18-19`）没有 `device_id/channel/family/replaced_by`；

**修法**：按 `docs/04 §2.1/§3` 冻结全量客户端 auth 路径与 DTO；补 refresh 安全字段/设备表；在契约/API 表列出权限点；角色枚举统一为 `super_admin`。
