## 3. P0（阻塞）

### P0-1 · `channel.json` schema/id/保留字与 `docs/09`/`docs/27` 权威定义冲突

- `spec.md:8-10`：schema 为 `id`、`edition`、`defaults.server_url`、`brand{name,powered_by,logo{light,dark},primary_color?}`、`strings`、`platforms`；保留字 `official/personal/enterprise`。
- `docs/09` §3 权威：
  - `identity.slug` / `identity.product_name` / `identity.app_id` / `identity.company` / `identity.copyright` / `identity.deep_link_scheme` / `identity.app_origin_scheme` / `identity.data_dir_name` / `identity.product_home_dir`；
  - `brand.logo.light/dark`（路径、canonicalize、256KB、禁 `<script>`/外链）、`brand.icon_source`、`brand.powered_by`；
  - `assets.accent`、`copy.*`、`strings/<locale>.json`（仅 `brand.*`）、`config/defaults.toml`；
  - 保留字 `official/beta/personal/demo/test`。
- `edition` 不属于 channel（channel 与 edition 正交，ADR-044；edition 在 `oem.toml.edition_base`/index），`platforms` 在 `oem.toml`，`strings` 是 locale 文件而非 channel.json 字段。
- 当前 `brands/official/channel.json` 也已使用 spec 的简化形状（`id/edition/brand.logo`），与 docs/09/27 冲突；**现有实现已被 spec 固化**，必须先统一。

**修法**：以 `docs/09` §3 + `docs/27` §4 为唯一 schema，更新 spec/design/tasks/acceptance 和 `brands/official/channel.json`；channel 不含 `edition`/`platforms`/`strings` 内联；保留字/正则严格按 docs/09；补 schema JSON + 负向用例（缺键/未知键/跨渠道唯一 app_id/scheme/data root/product_name）。

### P0-2 · `zk channel` 命令 API 与 docs/03 不一致，且当前不存在

- `spec.md:34` 验收与 `tasks.md:5` 用 `zk channel --check`；`docs/03:193` 定义的是 `zk channel validate --index <dir> --all` / `zk channel verify --channel C --dist`；`docs/09`/`docs/23` 也用全渠道校验。
- 当前 `./target/debug/zk channel --check` 实测 `unknown command: channel`；spec 却把它作为第一条验收。
- 结果：CI/acceptance 无法执行，且“渠道集/manifest/pin/品牌残留”校验没有确定的 CLI 契约。

**修法**：spec/tasks/acceptance 改用 docs/03 的 `zk channel validate|verify`（或先改 docs/03+ADR 并定义 `--check` 语义）；补 `zk channel validate --help` / 退出码 / 报告格式；acceptance 引用真实命令。

### P0-3 · 交付产物清单缺 `CLIENT-RELEASE.json`/`CHANNEL.json`/SBOM/VERSION，门户与 1:1 更新不可实现

- `spec.md:25-26` 只写“客户端三平台安装包、SHA256SUMS、服务端镜像”；`docs/09` §4–§5/§7 与 `docs/23` §3 要求：
  - `CLIENT-RELEASE.json`（镜像内 `/opt/zeokeel/client/`，门户/更新清单唯一版本源）；
  - `CHANNEL.json`（脱敏渠道身份）；
  - `SBOM/`（CycloneDX）、`VERSION`、`deploy/`、`HANDOVER.md`；
  - 镜像内三平台客户端 + `docker compose`/Caddy/portal。
- 没有 `CLIENT-RELEASE.json`，M5 退出条件“门户下载/1:1 更新”和 M5 更新校验无法落地；spec 的 `spec.md:29` 1:1 校验没有数据源。

**修法**：在 spec §3 明确交付树（docs/09/23 唯一命名），每渠道产物含 `CLIENT-RELEASE.json`/`CHANNEL.json`/`SHA256SUMS`/`SBOM/`/`VERSION`/`deploy/`；镜像内断言 `CLIENT-RELEASE.json` 与安装包 sha 一致；acceptance 加产物断言。

### P0-4 · 保留字/渠道身份规则与 docs/09 冲突，`edition` 进入 channel 破坏正交性

- `spec.md:9` 保留字 `official/personal/enterprise`；docs/09 保留字 `official/beta/personal/demo/test`。spec 允许 `beta/demo/test` 作 OEM，docs 禁止；spec 禁 `enterprise`，docs 未把 `enterprise` 列保留字（但 edition 正交，不应作为 channel）。
- `spec.md:8/10` 把 `edition` 放进 channel.json；docs/09/ADR-044 明确所有产物 = edition × channel，channel 不决定 edition；`oem.toml.edition_base`/`index.toml.edition` 才决定。
- 结果：`brands/official/channel.json` 当前写 `edition:"personal"`，官方企业版 channel 可能被误构建为 personal；C1/C2/C14 风险。

**修法**：保留字按 docs/09；channel 删 `edition`，edition 只从 edition/oem.toml/index 读取；补 `enterprise×official` 仍为 enterprise 的负向测试。

## 4. P1（应修）

1. **OEM index pin/submodule 不完整**：`spec.md:17` 只要求 `pin == gitlink`；docs/09 §2 要求 `.gitmodules` + submodule gitlink + `index.toml.pin` 三处一致；manifest 渠道集 vs `[channels]` 也要一致。补 `.gitmodules`/目录名/channel id/owner/depth 校验和 fixture 模拟说明。
2. **deep OEM 契约边界不完整**：`spec.md:20` 只说“覆盖实现角色，契约/内核不可覆盖”；未写 `[packages]` 角色白名单、包必须 `zk.toml` 四件套、契约 conformance、许可证/来源、`zk plan` 换包矩阵。补 docs/09 §2/§3 的深度门禁。
3. **跨渠道唯一性漏项**：spec 只强调 channel id；docs/09 要求 app_id/deep-link scheme/app origin scheme/data root/product_name 跨渠道唯一。补 manifest 全渠道校验与负向。
4. **品牌残留 `hide` 的实现口径不够**：`spec.md:12` 要求构建产物不得出现 “ZeoKeel”/官方 logo/域名；但 MIT `NOTICE`/`package name`/`channel.json` 等合法串需要明确 allowlist 与扫描范围（二进制 strings vs 文本源 vs 打包后）。补“官方模板+allowlist+产物重派生”规则，避免误报或漏报。
5. **构建期注入命名与 docs 不一致**：spec `brand.gen.{ts,rs}`/`channel.gen.{ts,rs}`；docs/09 §1.4/§3 与 docs/27 用 `brand.ts`/`brand.json`/`channel.json`。补唯一生成物路径、`@generated`、逐字节 `--check`、channel.json 随包分发。
6. **`platforms`/`strings` 位置**：spec 在 channel.json；docs/09 在 `oem.toml.platforms` + `strings/<locale>.json`/`config/`。按 docs 修正；门户按 platforms 收窄。
7. **门户/更新 1:1 未落到端点/清单**：spec 只说 `GET /api/updates/manifest`；未写 `CLIENT-RELEASE.json` 读取、channel/edition/version 字段、拒绝矩阵、门户无脚本 CSP。补 API/验收。
8. **macOS/Windows/Linux 交付证据不足**：spec 只说“CI 就绪”；未给 workflow job、证书缺失 dry-run 标记、Windows `SHA256SUMS` 文档、AppImage 校验。补 acceptance 命令/证据路径。
9. **升级演练无依赖/回滚细节**：spec `spec.md:30` 只说 dry-run；docs/20/09 §5 要求备份→sha→docker load→compose→readyz→失败回滚；tasks task7 依赖4但未依赖产物 task5。补脚本参数/证据/依赖。
10. **任务顺序**：task6（门户/更新）只依赖2，却需要 task5 的 `CLIENT-RELEASE.json`；task7 只依赖4，却需要 task5 产物；`tasks.md:10` 的 `packages/server/updates?` 是占位路径。补依赖/具体包路径。
11. **验收 false claim/未实现命令**：`acceptance.md:9` 的 `zk channel --check` 当前不存在；`scripts/oem-e2e.sh`/``upgrade-drill.sh` 不存在（实现前允许，但 acceptance 应写“创建任务”并区分 pending）。补任务/证据。
12. **proposal 无评审字段**：`proposal.md` 缺 `- 评审：`；C16/review-check 在 approved 前需补。
13. **demo 渠道 id 不一致**：spec/proposal 用 `oem-demo`；docs/09 示例用 `oem-acme`/`demo-oem-acme`。统一一个 demo id 并全文档引用。
14. **docs/09 与 docs/27 内部也有 schema 差异**（`identity.*` vs `brand.name`），M5 必须先收敛 docs/09/27，再写 spec；否则实现者无唯一 schema。
