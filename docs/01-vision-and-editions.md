# 01 · 产品形态、双版本与 OEM

> 本文件锁定"我们要交付什么"：企业版、个人版、OEM 三种产物，以及它们的边界与硬约束。
> 具体构建与交付流程见 `09-delivery-and-oem.md`；包与组合机制见 `02`、`03`。
> **最高优先级的设计原则见 [`00-design-principles.md`](00-design-principles.md)**：企业版遵循**弱管控**——
> 服务端只管身份/钱/商店/审计/构建期，客户端能力完整下发，工具/网络/审批不由服务端限制。

## 1. 一句话

**企业版**：一个能装进企业内网、员工装个客户端就能用 AI 的完整平台，AI 用量由服务端统一
网关与计费，技能/连接器/应用由管理员管控。
**个人版**：同一个客户端，去掉服务端依赖，用户自己配 provider，数据全在本地。
**OEM**：给白标客户交付企业版的"换品牌版本"，构建期注入，客户可深度定制。

## 1.5 版本模型：企业版 = 个人版 + 企业管控包

- **个人版是基线**：客户端壳、UI、本地 agent、工具、审批、会话、自配 provider、本地技能/MCP、GitHub Releases 更新。
- **企业版不另造客户端**：在个人版包集合之上**追加企业管控包**（登录/JWT、网关 provider、技能中心客户端、连接器客户端、WASM 应用客户端、服务端、管理台），
  并覆盖少数角色（`llm.provider.default`: 本地 → 网关；`client.update`: GitHub → 服务端；新增 `auth.client`），
  **同时排除个人版专属包**（本地 provider 设置 UI、GitHub 更新器、个人引导），避免两套 provider/更新器同时存在。
  公式：`enterprise = (personal − personal-only) + 企业管控包 + 角色覆盖`。
- 因此：**个人版先交付**；企业版是同一客户端 + 一组额外包 + 服务端；不存在两份客户端基线。
- **官方企业版也是一个渠道**（`official`）：默认 `server_url` 为空，客户登录时自己填服务器地址；
  OEM 渠道可预置地址实现免填。官方/OEM 走同一条渠道构建与测试链路（demo 渠道用于验证 OEM 能力）。
- 构建：`editions/enterprise.toml` 继承 `personal`（`base_edition = "personal"`），`exclude` 个人版专属包，追加企业包并覆盖角色；
  CI 证明企业版闭包 ⊇ 个人版闭包（除被覆盖/排除项），且不含 personal-only 包。

## 2. 三个产物对照

| 维度 | 企业版（Enterprise） | 个人版（Personal） | OEM 版 |
| --- | --- | --- | --- |
| 服务端 | ✅ 必须部署（docker compose） | ❌ 无 | ✅（可按客户定制） |
| 客户端 | ✅ | ✅ | ✅（品牌/文案/功能可换） |
| 登录 | 必须（本地/OIDC/LDAP 单一主源 + 应急超管） | 不需要 | 继承企业版（客户可换登录源品牌） |
| AI provider | **服务端下发，员工不可改** | 用户自己配置（DeepSeek/OpenAI 兼容/Ollama…） | 默认随客户配置；深度定制可换 provider 包 |
| AI 请求路径 | 客户端 → 服务端网关 → 上游 | 客户端 → 上游（用户 key） | 同企业版 |
| 计费 | 服务端计量 + 个人钱包 + 超额阻断 | 无（用户自己的 key） | 同企业版（价格/月发放可配，网关与审计不可关） |
| 技能 | 企业技能中心（上传/审批/可见范围 全员/指定用户/强制更新/删除同步） | 本地技能目录 | 企业版 + 客户内置技能 |
| 连接器 MCP | 管理员下发，密钥在服务端 | 用户本地自配 | 同企业版 |
| WASM 应用 | 服务端执行，客户端开窗 | ❌ 不提供 | 同企业版 |
| 管理台 | ✅（也是包，可 OEM） | ❌ | ✅ 可换皮 |
| 交付物 | docker 镜像导出包（内含客户端安装包 + 门户） | 三平台安装包 | 每客户镜像 + 三平台安装包 |
| 许可 | MIT | MIT | MIT（OEM 定制代码由我方开发并入库） |

## 3. 用户与场景

| 用户 | 场景 | 成功标准 |
| --- | --- | --- |
| 企业员工 | 登录客户端，用 AI 改代码/写文档/跑工具，用企业技能与连接器 | 开箱即用，不用自己配 key；超额时明确提示 |
| 企业管理员 | 部署 → 建用户 → 配 provider/峰谷价 → 审批技能 → 上下架应用 → 看用量 | 一处配置全端生效；可审计、可回滚 |
| 个人用户 | 下载客户端，填自己的 API key | 无服务端也能完整使用 agent 能力 |
| OEM 客户 | 拿到带自己品牌的镜像与安装包 | 品牌、文案、默认配置全换；升级不冲突 |
| 客户 IT | 内网离线部署、升级、备份 | 一个压缩包 + 一条 compose 命令 |

## 4. 功能范围（只列范围，规范见对应文档）

- 服务端域：认证/用户、钱包/配额、AI 网关、技能、连接器、应用、审计、管理台。规范分别在 `07`、`22`、`04`、`08`。
- 客户端：本地 agent/工具/审批/会话，登录、bootstrap、技能/连接器/应用客户端、更新。规范在 `05`、`19`、`09`。
- 个人版：纯客户端、无服务端/登录/应用中心、自配 provider、本地技能/MCP、GitHub Releases。规范在 `05`、`09`。
- 详细能力清单不再在此复制；避免与领域文档漂移。

## 5. 边界与非目标

- **不做多租户 SaaS**：一套部署服务一个企业（单租户），数据隔离靠部署/备份，不靠租户 ID。
- **不做部门/用户组**：已删除该功能；可见性为全员/指定用户。
- **不做部门预算**：只有个人钱包（已拍板）。
- **不做企业审批**：员工拥有客户端全部能力；危险操作由客户端本地审批（用户自己决定）。
- **不限制工具与网络**：默认全开、允许所有地址（安全责任在客户端与客户网络边界）。
- **服务端不跑 agent**：agent 循环只在客户端；服务端不执行用户工具调用。
- **WASM 应用不可调用 AI**（已拍板）：应用是数据处理/表单/小工具，AI 能力由客户端 agent 提供。
- **不做运行时插件市场/安装器**：所有包构建期组合；OEM 定制走构建流水线。
- **不做插件沙箱承诺**：同进程静态链接，安全投入在供应链、审计与网络边界。
- 不做 IDE、不做通用浏览器（参考实现有 browser，本规划范围外，可作为后续包）。

## 6. 版本与许可

| 版本 | 许可 | 说明 |
| --- | --- | --- |
| 企业版核心（同个人版） | MIT | 服务端/客户端源码开源，可自建 |
| 个人版 | MIT | 同上，构建裁剪 |
| OEM 产物 | MIT | OEM 定制代码由我方开发并入库；产物按合约分发（D61） |
| 第三方依赖 | 依各自许可 | `cargo-deny`/`license-check` 门禁；NOTICE 随产物 |

许可证与品牌边界：**MIT 不授予商标权**。企业版默认品牌为 ZeoKeel；OEM 客户用自己的品牌，
Powered by/署名策略按 D62（官方默认显示，OEM 默认隐藏）；商标不得暗示背书。

## 7. 对架构的直接约束

1. 客户端必须是**同一个二进制/安装包**能按 edition 裁剪——不能靠运行时开关（见 ADR-020）。
2. 服务端能力必须**包化**，以便 OEM 只换品牌/配置，或替换某个域的实现（ADR-021）。
3. 企业版客户端**不得包含**本地 provider 配置 UI 与密钥存储包；个人版**不得包含**登录/网关包。
   这是构建期裁剪，不是隐藏。
4. 企业版客户端首次启动即登录页：**OEM 渠道的服务端地址由 `channel.json` 内置，登录页只有账号/密码**；
   官方企业版渠道地址为空时，首配页允许输入并本地保存（设置可改，需重新登录）。未登录只显示登录页，无本地功能。
5. 所有服务端配置项要能被管理台修改并**热生效或明确要求重启**——不能写死在 env 里（参考实现教训）。
6. 版本升级要能在离线环境完成：镜像自包含、升级包带迁移、备份先行。
7. **企业版只锁三件事**：不能自配 provider/base_url/key（AI 走网关）、内容只能从企业商店安装、
   应用中心由服务端执行。其余客户端能力与个人版一致（工具全开、网络不限、本地审批可配、本地设置可用）。
